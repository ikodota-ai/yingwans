# MySQL 误删数据恢复手册（binlog 时间点恢复）

> 本手册基于 2026-09-20 真实事故整理：生产服务器误执行 `sql/kemovie.sql`（全量安装脚本，
> 含 11 条 `DROP TABLE IF EXISTS`），km_ 核心业务表被清空。通过 binlog 重放到删库前一刻，
> 零数据损失恢复。供再次遇到误删/误改时对照操作。

## 0. 原理：为什么 binlog 能救命

- MySQL 的 binlog 记录所有改变数据的语句和行事件；**DDL 无论哪种格式都以语句形式记录**。
- 只要 binlog 覆盖"建库 → 现在"的全程，就等于拥有任意时间点的恢复能力（不依赖备份的 PITR）。
- 核心思路：找到**破坏发生前一刻的 binlog 位置（stop-position）**，把 [起点, stop-position) 区间
  重放到库里，数据即回到破坏前。
- 前提条件：`log_bin=ON`，且最早的 binlog 文件时间早于建库时间。

## 1. 第一步：止血（比什么都重要）

发现误删后，**先防止二次伤害，再谈恢复**。

```bash
# 1) 立即备份当前状态（哪怕库已半空）——后续所有操作的回退锚点
mysqldump -h127.0.0.1 -uroot -p --single-transaction yingwans > ~/yingwans_now.sql
```

- `--single-transaction`：InnoDB 一致性快照备份，不锁表、不影响其他库。

```text
2) 停掉后端应用（jar），防止恢复期间程序继续写入，与恢复数据撞车。
3) 在恢复完成前，不要再执行任何 SQL 脚本。
```

## 2. 第二步：确认 binlog 可用

```sql
SHOW VARIABLES LIKE 'log_bin';   -- ON 才有救；OFF 则只能找备份
SHOW VARIABLES LIKE 'datadir';   -- binlog 文件所在目录，本次为 /usr/local/mysql/var/
SHOW BINARY LOGS;                -- 列出所有 binlog 文件及大小
```

若服务器 `mysqlbinlog` 命令不存在，先找自带路径：

```bash
ls /usr/local/mysql/bin/ | grep binlog   -- 手动安装的 MySQL 通常在这里，只是没进 PATH
```

## 3. 第三步：确认 binlog 起点覆盖建库时刻

```bash
# 看 binlog 第一个事件的时间（^#2 匹配时间戳注释行，如 #260528 = 2026-05-28）
/usr/local/mysql/bin/mysqlbinlog /usr/local/mysql/var/mysql-bin.000015 | grep -m1 "^#2"

# 确认目标表的建表语句在 binlog 里（在 = 从建库到现在全程有记录，可完整重建）
/usr/local/mysql/bin/mysqlbinlog /usr/local/mysql/var/mysql-bin.000015 | grep -im1 "create table.*km_media"
```

- 起点早于建库时间 → 可完整恢复；起点晚于建库 → 只能部分恢复（需结合旧备份）。
- 本次结论：`mysql-bin.000015` 无 yingwans 任何痕迹，整个库的生命周期都在 `000016` 里，只需处理一个文件。

## 4. 第四步：定位破坏点 stop-position（最关键一步）

```bash
# 把整个 binlog 解码成 SQL 文本（185M 的 binlog 解码后更大，放 /tmp 即可）
/usr/local/mysql/bin/mysqlbinlog /usr/local/mysql/var/mysql-bin.000016 > /tmp/bin16.sql

# 找删表语句（注意反引号要转义）
grep -n "DROP TABLE IF EXISTS \`km_media\`" /tmp/bin16.sql | head
```

**必须看懂的两个知识点**：

1. `DROP TABLE IF EXISTS t /* generated by server */` 不是客户端执行的语句，而是 MySQL 在每个
   **普通 CREATE TABLE** 写入 binlog 时自动补的幂等 DROP（保证重放/从库安全）。看到它 = 附近有一个建表事件。
2. `CREATE TABLE IF NOT EXISTS` **不会**有这种前置 DROP（语句本身幂等）——这是后面 km_provider
   恢复报错的根源，见第 6 步。

每个事件前的 `# at <数字>` 是 binlog 位置，`#260920 18:13:56` 是时间戳。用时间戳区分多次 DROP
哪次是事故（本次：9-13 21:23 是部署建表，9-20 18:13:56 是误删）。

```bash
# 看事故事件的上下文，取事件开头 # at 后面的数字
sed -n '行号-8,行号p' /tmp/bin16.sql
```

本次取到 `# at 185041955`，且事件中带 `SET @@session.foreign_key_checks=0`——正是 `kemovie.sql`
开头 `SET FOREIGN_KEY_CHECKS = 0;` 的特征，确认无误。

**区间纯净性验证**：从事故点往回到上一次 DDL 之间没有其他 DDL（只有数据写入），说明停在这里可以
完整恢复。本次两次 DDL 之间行号 6488192 → 7915143 无任何 DROP/CREATE，确认纯净。

## 5. 第五步：导出恢复 SQL

```bash
/usr/local/mysql/bin/mysqlbinlog \
  --skip-gtids \
  --database=yingwans \
  --stop-position=185041955 \
  /usr/local/mysql/var/mysql-bin.000016 > /tmp/rec_yingwans.sql
```

参数意图：

- `--skip-gtids`：剥离 GTID 事件，避免重放时与目标实例的 GTID 冲突。
- `--database=yingwans`：多库实例**必须加**，只提取该库事件。注意它按"默认数据库(USE)"过滤语句事件、
  按实际所属库过滤行事件。
- `--stop-position=N`：重放到 N 之前停止（不含 N 这个事件本身），N 即第四步的事故位置。

**导入前排两个暗坑**：

```bash
# 暗坑1：文件里若含 CREATE DATABASE，导入即报"库已存在"中断 → 有则删掉
grep -n "^CREATE DATABASE" /tmp/rec_yingwans.sql
sed -i '/^CREATE DATABASE/d' /tmp/rec_yingwans.sql

# 暗坑2：确认事故事件没被包进来（把 260920 换成事故当天日期）→ 必须无输出
grep -B3 "generated by server" /tmp/rec_yingwans.sql | grep "#260920"
```

## 6. 第六步：恢复导入（两种方式）

### 方式 A：直接导入生产库（本次采用）

本质 = **整库回滚到 stop-position**：rec 里包含建库时的 DROP+CREATE，会把现有表全部重建再灌数据。

```bash
# 确认：已备份、已停应用。然后导入——千万不要加 --force，报错立即停
mysql -h127.0.0.1 -uroot -p --default-character-set=utf8mb4 < /tmp/rec_yingwans.sql
```

**本次踩的坑：ERROR 1062 Duplicate entry '1' for key 'km_provider.PRIMARY'**

- 原因：`km_provider` 是用 `CREATE TABLE IF NOT EXISTS` 建的（见第 4 步知识点 2），binlog 没有前置
  自动 DROP；重放时建表语句空转（表已存在且有种子数据），随后 rec 里的 INSERT 与已有 id=1 撞车。
- 修复：

```sql
DROP TABLE yingwans.km_provider;   -- 它的数据 rec 里本来就有，删掉让重放自己重建
```

然后**从头重新完整导入**（文件开头的 DROP+CREATE 会把半成品状态清掉，重复劳动但干净）。

- 通用对策：
  - `Duplicate entry` → DROP 该表后重跑；
  - `Table doesn't exist` → 说明该表的 CREATE 被 `--database` 过滤掉了，先从当前库导出空结构
    （`mysqldump --no-data yingwans 表名 | mysql yingwans`）预建，再重跑。
- 导入中途报错中断后，库处于"回滚了一半"状态：**不要重试、不要 --force**，先分析错误。

### 方式 B：临时库验证后回迁（更稳，推荐下次优先用）

先在另一实例（如本地 Mac 的 MySQL）重放验证，确认无误再导回生产：

```bash
scp root@服务器:/tmp/rec_yingwans.sql ~/binlog-recovery/
mysql -uroot -p -e "CREATE DATABASE yingwans DEFAULT CHARSET utf8mb4"
mysql -uroot -p --default-character-set=utf8mb4 < ~/binlog-recovery/rec_yingwans.sql
```

- 注意：binlog_format=ROW 时行事件内嵌库名，不受 USE 重定向影响，所以"改个库名导到同实例的临时库"
  对行事件无效，必须用另一实例。
- 验证行数无误后，按需导回：`mysqldump` 出需要的表 → 生产库 TRUNCATE → 导入。

## 7. 第七步：验证与补结构

```sql
-- 数据量核对（应与删库前量级一致）
SELECT COUNT(*) FROM km_media;
SELECT COUNT(*) FROM km_member;
SELECT COUNT(*) FROM km_user_subscription;
SELECT COUNT(*) FROM km_mdl_source;

-- 表结构核对：恢复回来的表 = 删库前一刻的结构，之后的 ALTER 需要重补
SELECT COLUMN_NAME FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA='yingwans' AND TABLE_NAME='km_media'
  AND COLUMN_NAME IN ('letterboxd_slug','legacy_aid','tags','source',
                      'feishu_doc_token','feishu_doc_url','tencent_doc_url');
```

缺哪列就补跑对应的增量 `sql/kemovie_xxx.sql`。**铁律：`kemovie.sql` 只用于全新安装；有数据的库
只跑增量文件；跑之前先查列/表是否已存在。**

## 8. 第八步：收尾

1. 启动后端应用，验证前台列表/详情、后台各页面正常。
2. stop-position 之后的后台改动（改过的参数、手动加的数据）已丢失，检查并补做。
3. 建立每日备份（这次是靠 binlog 侥幸，下次未必）：

```bash
# crontab -e，每天凌晨 3 点备份，保留 14 天
0 3 * * * mysqldump -h127.0.0.1 -uroot -p'密码' --single-transaction yingwans | gzip > ~/backup/yingwans_$(date +\%F).sql.gz
0 4 * * * find ~/backup -name "yingwans_*.sql.gz" -mtime +14 -delete
```

## 9. 命令速查表

| 阶段 | 命令 | 一句话意图 |
| --- | --- | --- |
| 止血 | `mysqldump --single-transaction 库 > 备份.sql` | 留回退锚点 |
| 查 binlog | `SHOW BINARY LOGS;` | 看有哪些 binlog 文件 |
| 看起点 | `mysqlbinlog 文件 \| grep -m1 "^#2"` | binlog 覆盖到多早 |
| 找事故 | `mysqlbinlog 文件 > t.sql; grep -n "DROP TABLE" t.sql` | 定位删库事件 |
| 取位置 | `sed -n '行号-8,行号p' t.sql` | 读 `# at` 得 stop-position |
| 导出 | `mysqlbinlog --skip-gtids --database=库 --stop-position=N 文件 > rec.sql` | 截取 [起点,事故前) 区间 |
| 排坑 | `grep "^CREATE DATABASE" rec.sql` / 日期复查 | 防止导入即失败/取错区间 |
| 恢复 | `mysql 库 < rec.sql`（不加 --force） | 整库回滚到事故前 |
| 撞车 | `DROP TABLE 冲突表;` 后重跑 | IF NOT EXISTS 建的表需手动清 |
| 补结构 | information_schema 查列 + 跑增量 SQL | 把恢复后的旧结构升到最新 |

## 10. 经验教训（预防措施）

1. 含 `DROP TABLE` 的全量安装脚本（`kemovie.sql`、RuoYi 的 `ry_*.sql`）**永远不在有数据的库执行**；
   升级只用 `kemovie_xxx.sql` 增量文件。
2. 多库实例上每条 mysql 命令都**显式指定库名**，执行脚本前再三确认。
3. 任何 DDL 操作前先 `mysqldump` 单库备份，30 秒换一条命。
4. 保持 `log_bin=ON` 并确认保留期（`binlog_expire_logs_seconds`，建议 ≥ 7 天）——binlog 是最后防线。
5. `CREATE TABLE IF NOT EXISTS` 创建的表，重放时不会自动 DROP，主键冲突时先 DROP 再重跑。
